# सुरक्षा सख्तीकरण {/* #security-hardening */}

प्रोडक्शन हार्डनिंग के लिए **duplistatus** की सुविधाएँ परतदार और वैकल्पिक हैं। यहाँ वर्णित सभी सुविधाएँ डिफ़ॉल्ट रूप से बंद हैं, इसलिए एक नया इंस्टॉलेशन आपकी पसंद करने तक काम करता रहता है। तीन स्वतंत्र परतें हैं:

- **एपीआई कुंजियाँ** — बाहरी अपलोड और रीड एपीआई के लिए स्कोप्ड सीक्रेट्स; आमतौर पर होमलैब में सबसे आसान पहला कदम
- **आईपी अनुमति सूची** — व्यवस्थापक इंटरफेस, बाहरी एपीआई, या दोनों पर सीआईडीआर प्रतिबंध
- **HTTPS रिवर्स प्रॉक्सी** — एन्क्रिप्टेड ट्रैफिक, जिसमें पोर्ट `9666` पब्लिक इंटरनेट से बंद रखा जाता है

## अनुशंसित क्रम {/* #recommended-order */}

1. पोर्ट `9666` को पब्लिक इंटरनेट से बंद रखें: एप्लिकेशन को लोकलहोस्ट या एक निजी नेटवर्क पर बाइंड करें।
2. [एपीआई कुंजियाँ](#api-keys) बनाएं और **बाहरी एपीआई के लिए एपीआई कुंजियाँ आवश्यक हैं** सक्षम करें। यह रिवर्स प्रॉक्सी के बिना काम करता है और सबसे तेज़ परिणाम देता है।
3. [रिवर्स प्रॉक्सी के साथ HTTPS](#https-with-a-reverse-proxy) के माध्यम से **duplistatus** सर्व करें।
4. यदि आप अनुमति सूची का उपयोग करने की योजना बनाते हैं, तो **विश्वसनीय प्रॉक्सी** में प्रॉक्सी का टीसीपी पीयर पता जोड़ें (या `IP_TRUSTED_PROXIES`)
5. वैकल्पिक रूप से, व्यवस्थापक और बाहरी [आईपी अनुमति सूची](#ip-allowlist) सक्षम करें, **पता लगाया गया आईपी** और हाल ही के आईपी सुझावों का उपयोग करके, ताकि आप अपने आप को लॉक न करें।

## एपीआई कुंजियों और आईपी अनुमति सूची के साथ पहुँच प्रतिबंधित करें {/* #restrict-access-with-api-keys-and-ip-allowlists */}

ये दो सेटिंग्स सुविधाएँ सीमित करती हैं कि कौन सा डैशबोर्ड और बाहरी डेटा एपीआई तक पहुंच सकता है। वे स्वतंत्र हैं: जब दोनों सक्षम हैं, तो एक अनुरोध को **दोनों** जाँचों को पास करना होगा।

### एपीआई कुंजियाँ {/* #api-keys */}

[एपीआई कुंजियाँ](../user-guide/settings/api-keys-settings.md) होमलैब में जोड़ने का सबसे सरल सुरक्षा उपाय है। डुप्लिकेटी अपलोड और होमपेज विजेट्स के लिए स्कोप्ड सीक्रेट्स बनाएं, फिर उन्हें आवश्यक बनाएं — कोई रिवर्स प्रॉक्सी या सीआईडीआर योजना की आवश्यकता नहीं है।

| स्कोप | एंडपॉइंट्स |
|-------|-----------|
| अपलोड करें | `POST /api/upload` |
| पढ़ें | `GET /api/summary`, `GET /api/lastbackup/:id`, `GET /api/lastbackups/:id` |

कम से कम एक अपलोड कुंजी और एक पढ़ने की कुंजी बनाएँ **इससे पहले** कि आप **बाहरी एपीआई के लिए एपीआई कुंजियाँ आवश्यक हैं** को चालू करें। अन्यथा, डुप्लिकेटी अपलोड और होमपेज विजेट्स तुरंत बंद हो जाएंगे जैसे ही स्विच सक्षम हो जाता है।

duplicati अपने अनुरोधों में कस्टम हेडर शामिल नहीं कर सकता, इसलिए आपको रिपोर्ट URL में `?api_key=…` जोड़कर अपने API कुंजी प्रदान करनी होगी. ध्यान दें कि क्वेरी स्ट्रिंग का उपयोग रिवर्स प्रॉक्सी एक्सेस लॉग्स में API कुंजी का उजागर कर देता है. अन्य क्लाइंटों के लिए जो कस्टम हेडर का समर्थन करते हैं, अतिरिक्त सुरक्षा के लिए `X-Api-Key` हेडर या `Authorization: Bearer` हेडर का उपयोग करने की अनुशंसा की जाती है.

उपलोड आकार सीमा और उसी सेटिंग्स पेज पर प्रति-आईपी दर सीमाएं कुंजियों वैकल्पिक होने के दौरान भी लागू होती हैं। एपीआई कुंजियाँ बाहरी डेटा एपीआई को सुरक्षित करती हैं; वे व्यवस्थापक इंटरफेस को प्रतिबंधित नहीं करतीं, जो लॉगिन और, वैकल्पिक रूप से, व्यवस्थापक आईपी अनुमति सूची द्वारा सुरक्षित है।

### आईपी अनुमति सूची {/* #ip-allowlist */}

[आईपी अनुमति सूची](../user-guide/settings/ip-allowlist-settings.md) दो अलग-अलग सीआईडीआर सूचियां प्रदान करती है, दोनों डिफ़ॉल्ट रूप से बंद हैं:

- **व्यवस्थापक इंटरफेस** — पृष्ठ, लॉगिन, CSRF, और सत्र एपीआई
- **बाहरी एपीआई** — `/api/upload`, `/api/summary`, और `/api/lastbackup*`
- **स्वास्थ्य और पिंग** — `/api/health` और `/api/ping` दोनों सूचियों बंद होने पर सार्वजनिक रहते हैं। जब कोई सूची चालू होती है, तो वे लूपबैक के साथ-साथ व्यवस्थापक **aur** बाहरी सूची से CIDRs स्वीकार करते हैं, और गैर-लूपबैक क्लाइंट को रेट-लिमिट किया जाता है। ऐप-स्तरीय सीमाएँ एक वॉल्यूमेट्रिक कनेक्शन फ्लड को रोक नहीं सकती; यदि इंस्टेंस इंटरनेट-फेसिंग है, तो रिवर्स प्रॉक्सी पर `limit_req` / Caddy `rate_limit` जोड़ें।

किसी भी सूची को सक्षम करने से पहले, **सेटिंग्स → आईपी अनुमति सूची** पर **पता लगाया गया आईपी** जाँचें और **पीयर आईपी** को **अनुमति सूची आईपी** के साथ तुलना करें। **वर्तमान आईपी जोड़ें** या हाल ही के आईपी सुझावों का उपयोग करें ताकि आप अपने आप को लॉक न करें। पुनर्प्राप्ति कदम [आईपी अनुमति सूची द्वारा लॉक आउट](../user-guide/troubleshooting.md#locked-out-by-ip-allowlist) में हैं।

यदि **duplistatus** किसी रिवर्स प्रॉक्सी के पीछे बैठता है, तो पहले **विश्वसनीय प्रॉक्सी** कॉन्फ़िगर करें (नीचे देखें [आईपी अनुमति सूची के लिए विश्वसनीय प्रॉक्सी](#trusted-proxies-for-ip-allowlists))। इसके बिना, अनुमति सूची निर्णय प्रॉक्सी के पते के खिलाफ किए जाते हैं, न कि क्लाइंट के।

## रिवर्स प्रॉक्सी के साथ HTTPS {/* #https-with-a-reverse-proxy */}

प्रोडक्शन डिप्लॉयमेंट के लिए, **duplistatus** को रिवर्स प्रॉक्सी के पीछे HTTPS के माध्यम से सर्व करें। नीचे दिए गए उदाहरण दो लोकप्रिय विकल्पों को कवर करते हैं।

### विकल्प 1: Certbot (Let's Encrypt) के साथ Nginx {/* #option-1-nginx-with-certbot-lets-encrypt */}

[Nginx](https://nginx.org/) एक व्यापक रूप से उपयोग किया जाने वाला वेब सर्वर है जो रिवर्स प्रॉक्सी के रूप में कार्य कर सकता है, और [Certbot](https://certbot.eff.org/) लेट्स एन्क्रिप्ट से मुफ्त टीएलएस प्रमाणपत्र जारी करता है।

**पूर्वशर्तें:**

- एक डोमेन नाम जिसका डीएनएस ए (या एएएए) रिकॉर्ड आपके सर्वर को इंगित करता है
- आपके सिस्टम पर इंस्टॉल किया गया Nginx
- आपके ऑपरेटिंग सिस्टम के लिए इंस्टॉल किया गया Certbot

**चरण 1: Nginx और Certbot स्थापित करें**

ऊबंटू/डेबियन पर:

```bash
sudo apt update
sudo apt install nginx certbot python3-certbot-nginx
```

**चरण 2: Nginx कॉन्फ़िगरेशन बनाएं**

`/etc/nginx/sites-available/duplistatus` बनाएं:

```nginx
server {
    listen 80;
    server_name your-domain.com;

    # Nginx defaults to 1 MB, which is below the upload limit on
    # Settings → API Keys (5 MB by default). Keep this at or above it.
    client_max_body_size 10m;

    location / {
        proxy_pass http://localhost:9666;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

यह नमूना `X-Forwarded-For` और `X-Real-IP` को `$remote_addr` के साथ **ओवरराइट** करता है। `$proxy_add_x_forwarded_for` का उपयोग न करें: यह क्लाइंट द्वारा भेजे गए किसी भी चीज़ को ऐपेंड करता है, जिससे क्लाइंट-नियंत्रित मानों को एक हेडर में छोड़ दिया जाता है, जिस पर अलोवेलिस्ट निर्भर करते हैं।

**चरण 3: साइट को सक्षम करें और प्रमाणपत्र प्राप्त करें**

```bash
# Enable the site
sudo ln -s /etc/nginx/sites-available/duplistatus /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

# Obtain the TLS certificate
sudo certbot --nginx -d your-domain.com
```

Certbot आपके Nginx कॉन्फ़िगरेशन में TLS सेटिंग्स जोड़ता है और HTTP को HTTPS पर रीडायरेक्ट करता है। यह एक नवीकरण टाइमर भी इंस्टॉल करता है, जिसे आप निम्नलिखित के साथ सत्यापित कर सकते हैं:

```bash
sudo certbot renew --dry-run
```

**प्रलेखन:**

- [Nginx Documentation](https://nginx.org/en/docs/)
- [Certbot Documentation](https://certbot.eff.org/instructions)
- [Let's Encrypt Documentation](https://letsencrypt.org/docs/)

### विकल्प 2: Caddy {/* #option-2-caddy */}

[Caddy](https://caddyserver.com/) एक आधुनिक वेब सर्वर है जो TLS प्रमाणपत्रों को स्वचालित रूप से प्राप्त और नवीकृत करता है, जिससे अधिकांश प्रमाणपत्र प्रबंधन कार्य हट जाता है।

**पूर्वशर्तें:**

- एक डोमेन नाम जिसका DNS A (या AAAA) रिकॉर्ड आपके सर्वर को इशारा करता है
- आपके प्रणाली पर इंस्टॉल किया गया Caddy

**चरण 1: Caddy स्थापित करें**

अपने ऑपरेटिंग सिस्टम के लिए [अधिकृत स्थापना गाइड](https://caddyserver.com/docs/install) का पालन करें।

**चरण 2: Caddyfile बनाएँ**

पैकेज इंस्टॉलेशन `/etc/caddy/Caddyfile` को पढ़ते हैं। इसके सामग्री को निम्नलिखित सेट करें:

```caddy
your-domain.com {
    reverse_proxy localhost:9666
}
```

Caddy का `reverse_proxy` निर्देश आपके लिए क्लाइंट आईपी हेडर सेट करता है। जब आप आईपी अनुमति सूचियों का उपयोग करते हैं, तो आपको **विश्वसनीय प्रॉक्सी** के तहत प्रॉक्सी के टीसीपी पीयर पते को सूचीबद्ध करना होगा (देखें [नीचे](#trusted-proxies-for-ip-allowlists)).

**चरण 3: Caddy को स्टार्ट या रीलोड करें**

यदि आपने पैकेज से Caddy इंस्टॉल किया है, तो मैनेज्ड सर्विस के माध्यम से कॉन्फ़िगरेशन लागू करें:

```bash
sudo systemctl reload caddy
```

Caddy को मैन्युअल रूप से चलाने के लिए — उदाहरण के लिए वर्तमान निर्देशिका में एक Caddyfile से — पहले मैनेज्ड सर्विस को रोकें ताकि पोर्ट 80 और 443 मुक्त हो जाएँ, फिर चलाएँ:

```bash
sudo caddy run --config Caddyfile
```

Caddy पहली बार साइट को सर्व करने पर प्रमाणपत्र प्राप्त करता है और इसे समाप्ति से पहले नवीकृत करता है।

**प्रलेखन:**

- [Caddy प्रलेखन](https://caddyserver.com/docs/)
- [Caddy रिवर्स प्रॉक्सी गाइड](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

### आईपी अनुमति सूची के लिए विश्वसनीय प्रॉक्सी {/* #trusted-proxies-for-ip-allowlists */}

लोकलहोस्ट या एक निजी नेटवर्क पर **duplistatus** को बाइंड करें ताकि रिवर्स प्रॉक्सी ही एकमात्र सार्वजनिक लिस्टनर हो। पोर्ट `9666` को इंटरनेट से पहुंचने योग्य नहीं होना चाहिए।

जब [आईपी अलोवेलिस्ट](../user-guide/settings/ip-allowlist-settings.md) सक्षम हैं, तो प्रॉक्सी को **Trusted proxies** में सूचीबद्ध करें (या `IP_TRUSTED_PROXIES` सेट करें)। एप्लिकेशन `X-Forwarded-For` और `X-Real-IP` को केवल तब मानता है जब TCP पीअर एक विश्वसनीय प्रॉक्सी है; अन्यथा यह उन्हें अनदेखा करता है।

- प्रॉक्सी को उन हेडर्स को कनेक्टिंग क्लाइंट के एड्रेस के साथ **ओवरराइट** करने के लिए कॉन्फ़िगर करें, जैसे कि ऊपर दिए गए Nginx नमूने में। ऐपेंड न करें।
- जब प्रॉक्सी होस्ट पर चलता है और **duplistatus** एक कंटेनर में चलता है, तो **Peer IP** आमतौर पर डॉकर ब्रिज गेटवे होता है (उदाहरण के लिए `172.17.0.1`)। उस एड्रेस या CIDR को **Trusted proxies** में डालें, और वास्तविक क्लाइंट CIDRs को एडमिन या बाहरी अलोवेलिस्ट में डालें।
- एक अलोवेलिस्ट सक्षम करने से पहले, **Settings → IP Allowlist** खोलें और **Detected IP** चेक करें: **Peer IP** प्रॉक्सी (या ब्रिज गेटवे) होना चाहिए और **Allowlist IP** क्लाइंट होना चाहिए। यदि Allowlist IP अभी भी प्रॉक्सी दिखा रहा है, तो ट्रस्टेड-प्रॉक्सी कॉन्फ़िगरेशन अभी तक सही नहीं है।

### HTTPS सक्षम करने के बाद {/* #after-enabling-https */}

```bash
--send-http-json-urls=https://your-domain.com/api/upload
```

:::info[महत्वपूर्ण]
अपने Duplicati सर्वर कॉन्फ़िगरेशन को HTTPS URL का उपयोग करने के लिए अपडेट करें:


API कुंजियाँ आवश्यक हैं तो `?api_key=YOUR_UPLOAD_KEY` ऐपेंड करें। Duplicati 2.0.9.106 से पुराने पर `--send-http-url=https://your-domain.com/api/upload` का उपयोग करें साथ ही `--send-http-result-output-format=Json`। [Duplicati Server Configuration](duplicati-server-configuration.md) देखें।

- `your-domain.com` को अपने डोमेन से बदलें, उदाहरणों में पूरे तरह से।
- प्रमाणपत्र का अनुरोध करने से पहले, अपने सर्वर के DNS A (या AAAA) रिकॉर्ड के अपने डोमेन के लिए रिज़ॉल्व हो गए हैं, यह सुनिश्चित करें।
- दोनों विकल्प प्रमाणपत्रों को स्वचालित रूप से नवीनीकृत करते हैं: सर्टबॉट के माध्यम से अपने सिस्टमडी टाइमर के माध्यम से, और कैडी के माध्यम से अपने बिल्ट-इन प्रमाणपत्र मैनेजर के माध्यम से।
- होस्ट फ़ायरवॉल को पोर्ट 443 तक सीमित करें, और `80` और `9666` को बाहर बंद रखें.
:::
