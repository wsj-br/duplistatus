# सुरक्षा हार्डनिंग {/* #security-hardening */}

**duplistatus** के लिए प्रोडक्शन हार्डनिंग स्तरित और वैकल्पिक है। यहां वर्णित प्रत्येक सुविधा डिफ़ॉल्ट रूप से बंद है, इसलिए एक नया इंस्टॉलेशन तब तक काम करता रहता है जब तक कि आप इसे सक्षम करना न चुनें। इसके तीन स्वतंत्र स्तर हैं:

- **API कुंजियाँ** — बाहरी अपलोड और रीड API के लिए स्कोप्ड सीक्रेट्स; आमतौर पर होमलैब में सबसे आसान पहला कदम
- **IP अनुमति सूचियाँ** — एडमिन इंटरफ़ेस, बाहरी API, या दोनों पर CIDR प्रतिबंध
- **HTTPS रिवर्स प्रॉक्सी** — एन्क्रिप्टेड ट्रैफ़िक, जिसमें पोर्ट `9666` को सार्वजनिक इंटरनेट से दूर रखा जाता है

## अनुशंसित क्रम {/* #recommended-order */}

1. पोर्ट `9666` को सार्वजनिक इंटरनेट से दूर रखें: एप्लिकेशन को localhost या किसी निजी नेटवर्क से बाइंड करें।
2. [API कुंजियाँ](#api-keys) बनाएं और **बाहरी API के लिए API कुंजियाँ अनिवार्य करें** सक्षम करें। यह रिवर्स प्रॉक्सी के बिना काम करता है और सबसे तेज़ तरीका है।
3. [HTTPS के साथ रिवर्स प्रॉक्सी](#https-with-a-reverse-proxy) के माध्यम से **duplistatus** को सर्व करें।
4. यदि आप अनुमति सूचियों का उपयोग करने का इरादा रखते हैं, तो प्रॉक्सी का TCP पीयर पता **विश्वसनीय प्रॉक्सी** (या `IP_TRUSTED_PROXIES`) में जोड़ें।
5. वैकल्पिक रूप से, खुद को लॉक आउट करने से बचने के लिए **पहचाना गया IP** और हाल के IP सुझावों का उपयोग करते हुए, एडमिन और बाहरी [IP अनुमति सूची](#ip-allowlist) को सक्षम करें।

## API कुंजियों और IP अनुमति सूचियों के साथ एक्सेस प्रतिबंधित करें {/* #restrict-access-with-api-keys-and-ip-allowlists */}

ये दो सेटिंग्स सुविधाएँ यह सीमित करती हैं कि डैशबोर्ड और बाहरी डेटा API तक कौन पहुँच सकता है। वे स्वतंत्र हैं: जब दोनों सक्षम होते हैं, तो अनुरोध को **दोनों** जाँचों को पास करना होगा।

### API कुंजियाँ {/* #api-keys */}

[API कुंजियाँ](../user-guide/settings/api-keys-settings.md) जोड़ना सबसे सरल सुरक्षा उपाय है, विशेषकर होमलैब में। Duplicati अपलोड और Homepage विजेट के लिए स्कोप्ड सीक्रेट्स बनाएं, फिर उन्हें अनिवार्य करें — किसी रिवर्स प्रॉक्सी या CIDR प्लानिंग की आवश्यकता नहीं है।

| स्कोप | एंडपॉइंट्स |
|-------|-----------|
| अपलोड करें | `POST /api/upload` |
| पढ़ें | `GET /api/summary`, `GET /api/lastbackup/:id`, `GET /api/lastbackups/:id` |

**बाहरी API के लिए API कुंजियाँ अनिवार्य करें** चालू करने से **पहले** कम से कम एक अपलोड कुंजी और एक रीड कुंजी बनाएं। अन्यथा जैसे ही स्विच सक्षम होता है, Duplicati अपलोड और Homepage विजेट काम करना बंद कर देते हैं।

Duplicati अपने अनुरोधों में कस्टम हेडर शामिल नहीं कर सकता है, इसलिए आपको रिपोर्ट URL में `?api_key=…` जोड़कर इसकी API कुंजी प्रदान करनी होगी। ध्यान दें कि क्वेरी स्ट्रिंग का उपयोग करने से रिवर्स प्रॉक्सी एक्सेस लॉग में API कुंजी एक्सपोज़ हो जाती है। कस्टम हेडर का समर्थन करने वाले अन्य क्लाइंट्स के लिए, अतिरिक्त सुरक्षा के लिए इसके बजाय `X-Api-Key` हेडर या `Authorization: Bearer` हेडर का उपयोग करने की अनुशंसा की जाती है।

उसी सेटिंग्स पृष्ठ पर अपलोड आकार सीमा और प्रति-IP दर सीमाएँ तब भी लागू होती हैं जब कुंजियाँ वैकल्पिक हों। API कुंजियाँ केवल बाहरी डेटा API की सुरक्षा करती हैं; वे एडमिन इंटरफ़ेस को प्रतिबंधित नहीं करती हैं, जो लॉगिन द्वारा और वैकल्पिक रूप से एडमिन IP अनुमति सूची द्वारा सुरक्षित है।

### IP अनुमति सूची {/* #ip-allowlist */}

[IP अनुमति सूची](../user-guide/settings/ip-allowlist-settings.md) दो अलग-अलग CIDR सूचियाँ प्रदान करती है, दोनों डिफ़ॉल्ट रूप से बंद हैं:

- **एडमिन इंटरफ़ेस** — पृष्ठ, लॉगिन, CSRF, और सत्र API
- **बाहरी API** — `/api/upload`, `/api/summary`, और `/api/lastbackup*`
- **हेल्थ और पिंग** — जब तक दोनों सूचियाँ बंद हैं तब तक `/api/health` और `/api/ping` सार्वजनिक रहते हैं। जब कोई भी सूची चालू होती है, तो वे लूपबैक और एडमिन **या** बाहरी सूची से CIDR स्वीकार करते हैं, और गैर-लूपबैक क्लाइंट दर-सीमित होते हैं। ऐप-स्तरीय सीमाएं भारी कनेक्शन बाढ़ को नहीं रोकती हैं; यदि इंस्टेंस इंटरनेट-फेसिंग है तो रिवर्स प्रॉक्सी पर `limit_req` / Caddy `rate_limit` जोड़ें।

किसी भी सूची को सक्षम करने से पहले, **सेटिंग्स → IP अनुमति सूची** पर **पहचाना गया IP** जांचें और **अनुमति सूची IP** के साथ **पीयर IP** की तुलना करें। **वर्तमान IP जोड़ें** या हाल के IP सुझावों का उपयोग करें ताकि आप खुद को लॉक आउट न करें। रिकवरी चरण [IP अनुमति सूची द्वारा लॉक किया गया](../user-guide/troubleshooting.md#locked-out-by-ip-allowlist) में हैं।

यदि **duplistatus** रिवर्स प्रॉक्सी के पीछे है, तो पहले **विश्वसनीय प्रॉक्सी** कॉन्फ़िगर करें (नीचे [IP अनुमति सूचियों के लिए विश्वसनीय प्रॉक्सी](#trusted-proxies-for-ip-allowlists) देखें)। इसके बिना, अनुमति सूची के निर्णय क्लाइंट के बजाय प्रॉक्सी के पते के आधार पर लिए जाते हैं।

## रिवर्स प्रॉक्सी के साथ HTTPS {/* #https-with-a-reverse-proxy */}

प्रोडक्शन डिप्लॉयमेंट के लिए, रिवर्स प्रॉक्सी के पीछे HTTPS पर **duplistatus** को सर्व करें। नीचे दिए गए उदाहरण दो लोकप्रिय विकल्पों को कवर करते हैं।

### विकल्प 1: Certbot (Let's Encrypt) के साथ Nginx {/* #option-1-nginx-with-certbot-lets-encrypt */}

[Nginx](https://nginx.org/) एक व्यापक रूप से उपयोग किया जाने वाला वेब सर्वर है जो रिवर्स प्रॉक्सी के रूप में कार्य कर सकता है, और [Certbot](https://certbot.eff.org/) Let's Encrypt से मुफ़्त TLS प्रमाणपत्र जारी करता है।

**पूर्वापेक्षाएँ:**

- एक डोमेन नाम जिसका DNS A (या AAAA) रिकॉर्ड आपके सर्वर की ओर इंगित करता है
- आपके सिस्टम पर Nginx इंस्टॉल हो
- आपके ऑपरेटिंग सिस्टम के लिए Certbot इंस्टॉल हो

**चरण 1: Nginx और Certbot इंस्टॉल करें**

चालू Ubuntu/Debian पर:

```bash
sudo apt update
sudo apt install nginx certbot python3-certbot-nginx
```

**चरण 2: Nginx कॉन्फ़िगरेशन बनाएं**

`/etc/nginx/sites-available/duplistatus` बनाएं:

```nginx
server {
    listen 80;
    server_name your-domain.com;

    # Nginx defaults to 1 MB, which is below the upload limit on
    # Settings → API Keys (5 MB by default). Keep this at or above it.
    client_max_body_size 10m;

    location / {
        proxy_pass http://localhost:9666;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

यह नमूना `X-Forwarded-For` और `X-Real-IP` को `$remote_addr` से **ओवरराइट करता है**। इसके बजाय `$proxy_add_x_forwarded_for` का उपयोग न करें: यह क्लाइंट द्वारा जो कुछ भी भेजा गया है उसमें जोड़ता है, जिससे एक ऐसे हेडर में क्लाइंट-नियंत्रित मान रह जाते हैं जिस पर अनुमति सूचियां निर्भर करती हैं।

**चरण 3: साइट सक्षम करें और प्रमाणपत्र प्राप्त करें**

```bash
# Enable the site
sudo ln -s /etc/nginx/sites-available/duplistatus /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

# Obtain the TLS certificate
sudo certbot --nginx -d your-domain.com
```

Certbot आपके Nginx कॉन्फ़िगरेशन में TLS सेटिंग्स जोड़ता है और HTTP को HTTPS पर रीडायरेक्ट करता है। यह एक नवीनीकरण टाइमर भी इंस्टॉल करता है, जिसे आप इसके साथ सत्यापित कर सकते हैं:

```bash
sudo certbot renew --dry-run
```

**दस्तावेज़ीकरण:**

- [Nginx दस्तावेज़ीकरण](https://nginx.org/en/docs/)
- [Certbot दस्तावेज़ीकरण](https://certbot.eff.org/instructions)
- [Let's Encrypt दस्तावेज़ीकरण](https://letsencrypt.org/docs/)

### विकल्प 2: Caddy {/* #option-2-caddy */}

[Caddy](https://caddyserver.com/) एक आधुनिक वेब सर्वर है जो TLS प्रमाणपत्र स्वचालित रूप से प्राप्त करता है और नवीनीकृत करता है, जिससे प्रमाणपत्र प्रबंधन का अधिकांश काम समाप्त हो जाता है।

**पूर्वापेक्षाएँ:**

- एक डोमेन नाम जिसका DNS A (या AAAA) रिकॉर्ड आपके सर्वर की ओर इंगित करता है
- आपके सिस्टम पर Caddy इंस्टॉल हो

**चरण 1: Caddy इंस्टॉल करें**

अपने ऑपरेटिंग सिस्टम के लिए [आधिकारिक इंस्टॉलेशन गाइड](https://caddyserver.com/docs/install) का पालन करें।

**चरण 2: Caddyfile बनाएं**

पैकेज इंस्टॉलेशन `/etc/caddy/Caddyfile` को पढ़ते हैं। इसकी सामग्री को इस प्रकार सेट करें:

```caddy
your-domain.com {
    reverse_proxy localhost:9666
}
```

Caddy का `reverse_proxy` निर्देश आपके लिए क्लाइंट IP हेडर सेट करता है। IP अनुमति सूचियों का उपयोग करते समय आपको अभी भी **विश्वसनीय प्रॉक्सी** के अंतर्गत प्रॉक्सी का TCP पीयर पता सूचीबद्ध करना होगा (नीचे [देखें](#trusted-proxies-for-ip-allowlists))।

**चरण 3: Caddy प्रारंभ या पुनः लोड करें**

यदि आपने Caddy को किसी पैकेज से इंस्टॉल किया है, तो प्रबंधित सेवा के माध्यम से कॉन्फ़िगरेशन लागू करें:

```bash
sudo systemctl reload caddy
```

इसके बजाय Caddy को मैन्युअल रूप से चलाने के लिए — उदाहरण के लिए वर्तमान डायरेक्टरी में मौजूद Caddyfile से — पोर्ट 80 और 443 को खाली करने के लिए पहले प्रबंधित सेवा को रोकें, फिर चलाएं:

```bash
sudo caddy run --config Caddyfile
```

Caddy पहली बार साइट प्रस्तुत करते समय प्रमाणपत्र प्राप्त करता है और उसकी समाप्ति से पहले उसे नवीनीकृत करता है।

**दस्तावेज़ीकरण:**

- [Caddy दस्तावेज़ीकरण](https://caddyserver.com/docs/)
- [Caddy रिवर्स प्रॉक्सी गाइड](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

### IP अनुमति सूचियों के लिए विश्वसनीय प्रॉक्सी {/* #trusted-proxies-for-ip-allowlists */}

**duplistatus** को लोकलहोस्ट या किसी निजी नेटवर्क से बाइंड करें ताकि रिवर्स प्रॉक्सी ही एकमात्र सार्वजनिक लिसनर हो। पोर्ट `9666` इंटरनेट से कभी भी एक्सेस करने योग्य नहीं होना चाहिए।

जब [IP अनुमति सूची](../user-guide/settings/ip-allowlist-settings.md) सक्षम हो, तो **विश्वसनीय प्रॉक्सी** के अंतर्गत प्रॉक्सी को सूचीबद्ध करें (या `IP_TRUSTED_PROXIES` सेट करें)। एप्लिकेशन `X-Forwarded-For` और `X-Real-IP` का सम्मान केवल तभी करता है जब TCP पीयर एक विश्वसनीय प्रॉक्सी हो; अन्यथा वह उन्हें अनदेखा कर देता है।

- ऊपर दिए गए Nginx नमूने की तरह, कनेक्ट होने वाले क्लाइंट के पते के साथ उन हेडर को **ओवरराइट** करने के लिए प्रॉक्सी को कॉन्फ़िगर करें। आगे न जोड़ें (append न करें)।
- जब प्रॉक्सी होस्ट पर चलती है और **duplistatus** कंटेनर में चलता है, तो **पीयर IP** आमतौर पर Docker ब्रिज गेटवे (उदाहरण के लिए `172.17.0.1`) होता है। उस पते या CIDR को **विश्वसनीय प्रॉक्सी** में डालें, और वास्तविक क्लाइंट CIDR को एडमिन या बाहरी अनुमति सूची में डालें।
- अनुमति सूची को सक्षम करने से पहले, **सेटिंग्स → IP अनुमति सूची** खोलें और **पहचाना गया IP** जांचें: **पीयर IP** प्रॉक्सी (या ब्रिज गेटवे) होना चाहिए और **अनुमति सूची IP** क्लाइंट होना चाहिए। यदि अनुमति सूची IP अभी भी प्रॉक्सी दिखाता है, तो विश्वसनीय-प्रॉक्सी कॉन्फ़िगरेशन अभी तक सही नहीं है।

### HTTPS सक्षम करने के बाद {/* #after-enabling-https */}

```bash
--send-http-json-urls=https://your-domain.com/api/upload
```

:::info[महत्वपूर्ण]
HHTTPS URL का उपयोग करने के लिए अपने Duplicati सर्वर कॉन्फ़िगरेशन को अपडेट करें:


यदि API कुंजियाँ आवश्यक हैं तो `?api_key=YOUR_UPLOAD_KEY` जोड़ें। 2.0.9.106 से पुराने Duplicati पर, `--send-http-result-output-format=Json` के साथ `--send-http-url=https://your-domain.com/api/upload` का उपयोग करें। [Duplicati सर्वर कॉन्फ़िगरेशन](duplicati-server-configuration.md) देखें।
:::

:::tip

- उदाहरणों में `your-domain.com` को अपने स्वयं के डोमेन से बदलें।
- प्रमाणपत्र का अनुरोध करने से पहले पुष्टि करें कि डोमेन का DNS A (या AAAA) रिकॉर्ड आपके सर्वर पर रिज़ॉल्व होता है।
- दोनों विकल्प प्रमाणपत्रों को स्वचालित रूप से नवीनीकृत करते हैं: Certbot अपने systemd टाइमर के माध्यम से, Caddy अपने अंतर्निहित प्रमाणपत्र प्रबंधक के माध्यम से।
- होस्ट फ़ायरवॉल को पोर्ट 443 तक सीमित रखें, और `80` और `9666` को बाहर के लिए बंद रखें।
:::
