# समस्या निवारण {/* #troubleshooting */}

### डैशबोर्ड लोड नहीं हो रहा है {/* #dashboard-not-loading */}
- जांचें कि क्या कंटेनर चल रहा है: `docker ps`
- पुष्टि करें कि पोर्ट 9666 पहुंच योग्य है
- कंटेनर लॉग जांचें: `docker logs duplistatus`
- यदि आप रिवर्स प्रॉक्सी का उपयोग कर रहे हैं, तो त्रुटियों के लिए रिवर्स प्रॉक्सी लॉग जांचें
- यदि आप IP अनुमति सूची का उपयोग कर रहे हैं, तो त्रुटियों के लिए IP अनुमति सूची लॉग जांचें

### कोई बैकअप डेटा नहीं {/* #no-backup-data */}
- Duplicati सर्वर कॉन्फ़िगरेशन की पुष्टि करें
- सर्वर के बीच नेटवर्क कनेक्टिविटी जांचें
- त्रुटियों के लिए duplistatus लॉग समीक्षा करें
- सुनिश्चित करें कि बैकअप जॉब्स चल रहे हैं
- यदि API कुंजियों का उपयोग कर रहे हैं, तो सुनिश्चित करें कि API कुंजी सही है, स्कोप सही है और समाप्त नहीं हुआ है (एक पढ़ने की कुंजी अपलोड नहीं कर सकती)

### सूचनाएं काम नहीं कर रही हैं {/* #notifications-not-working */}
- सूचना कॉन्फ़िगरेशन जांचें
- NTFY सर्वर कनेक्टिविटी की पुष्टि करें (यदि NTFY का उपयोग कर रहे हैं)
- सूचना सेटिंग्स का परीक्षण करें
- सूचना लॉग जांचें

### नए बैकअप दिखाई नहीं दे रहे हैं {/* #new-backups-not-showing */}

यदि आप Duplicati सर्वर चेतावनियां जैसे `HTTP Response request failed for:` और `Failed to send message: System.Net.Http.HttpRequestException:` देखते हैं, और नए बैकअप डैशबोर्ड या बैकअप इतिहास में दिखाई नहीं देते हैं:

- **Duplicati कॉन्फ़िगरेशन जांचें**: पुष्टि करें कि Duplicati को **duplistatus** को JSON भेजने के लिए सही ढंग से कॉन्फ़िगर किया गया है। Duplicati 2.0.9.106 और बाद के संस्करणों में, `--send-http-json-urls` का उपयोग करें जो `/api/upload` की ओर इंगित करता है। पुराने Duplicati में, `--send-http-url` के साथ `--send-http-result-output-format=Json` का उपयोग करें। देखें [Duplicati सर्वर कॉन्फ़िगरेशन](../installation/duplicati-server-configuration.md)।
- **नेटवर्क कनेक्टिविटी जांचें**: सुनिश्चित करें कि Duplicati सर्वर **duplistatus** सर्वर से कनेक्ट हो सकता है। पुष्टि करें कि पोर्ट सही है (डिफ़ॉल्ट: `9666`)।
- **HTTP 401**: API कुंजियों की आवश्यकता होती है और अपलोड URL में एक मान्य अपलोड-स्कोप कुंजी गायब है। [API कुंजियाँ](settings/api-keys-settings.md) में वर्णित के रूप में `?api_key=` जोड़ें।
- **HTTP 403**: कुंजी स्कोप गलत है (एक पढ़ने की कुंजी अपलोड नहीं कर सकती), या Duplicati होस्ट [बाह्य API IP अनुमति सूची](settings/ip-allowlist-settings.md) पर नहीं है।
- **HTTP 413**: JSON रिपोर्ट अपलोड आकार सीमा (डिफ़ॉल्ट 5 MB) से बड़ी है। `--send-http-max-log-lines` को कम करें या सेटिंग्स → API कुंजियाँ में सीमा बढ़ाएं।
- **HTTP 429**: प्रति-IP अपलोड दर सीमा पार हो गई थी। `Retry-After` के लिए प्रतीक्षा करें, या यदि कई जॉब्स एक ही समय में समाप्त होते हैं तो सीमाएं बढ़ाएं।
- **Duplicati लॉग समीक्षा करें**: Duplicati लॉग में HTTP अनुरोध त्रुटियों की जांच करें।
- **डुअल रिपोर्टिंग**: यदि आप [Duplicati मॉनिटरिंग](https://www.duplicati-monitoring.com/) को फॉर्म रिपोर्ट भी भेजते हैं, तो उस सेवा से एक विफलता या HTTP 500 Duplicati को **duplistatus** को JSON रिपोर्ट भेजने से रोक सकती है। फॉर्म URL पहले भेजे जाते हैं। देखें [duplistatus और Duplicati मॉनिटरिंग को रिपोर्टिंग](../installation/duplicati-server-configuration.md#reporting-to-duplistatus-and-duplicati-monitoring)।

### डैशबोर्ड पर डुप्लिकेट सर्वर {/* #duplicate-servers-on-the-dashboard */}

यदि डैशबोर्ड पर एक ही सर्वर एक से अधिक बार दिखाई देता है, तो यह अक्सर [बैकअप लॉग एकत्र करने](collect-backup-logs.md) के बाद, या Duplicati सर्वर को पुनः स्थापित करने या अपग्रेड करने के बाद होता है।

**कारण:**

- **बदला हुआ `machine_id`**: जब आप Duplicati को पुनः स्थापित या अपग्रेड करते हैं, तो सर्वर का `machine_id` बदल सकता है, और फिर **duplistatus** इसे एक नया सर्वर के रूप में मानता है।
- **Duplicati API बग**: Duplicati के नए संस्करणों में एक बग है जहां कुछ API एंडपॉइंट `identity` आईडी और `machine_id` को मिला देते हैं। यह असंगति **duplistatus** को एक ही सर्वर को अलग-अलग आईडी के तहत पंजीकृत करने का कारण बनती है, जिससे डुप्लिकेट उत्पन्न होते हैं।

**ठीक करें:**

1.  **Duplicati सर्वर** पर, निम्नलिखित में से **एक** करें:
    - `identity.txt` और `machineid.txt` फ़ाइलों को संपादित करें ताकि दोनों फ़ाइलों में **समान** आईडी हो; या
    - **Duplicati → सेटिंग्स → उन्नत विकल्प → मशीन-आईडी** खोलें और एक मान सेट करें (यह स्वतः भरा जाता है — केवल सुझाए गए मान को स्वीकार करें)।
2.  परिवर्तन प्रभावी हो इसके लिए Duplicati सर्वर को **पुनरारंभ** करें।
3.  **duplistatus** में, [सेटिंग्स → डेटाबेस रखरखाव → डुप्लिकेट सर्वर मर्ज करें](settings/database-maintenance.md#merge-duplicate-servers) का उपयोग करके डुप्लिकेट प्रविष्टियों को एकीकृत करें।

### सूचनाएं काम नहीं कर रही हैं (विस्तृत) {/* #notifications-not-working-detailed */}

यदि सूचनाएं भेजी या प्राप्त नहीं की जा रही हैं:

- **NTFY कॉन्फ़िगरेशन जांचें**: सुनिश्चित करें कि NTFY URL और विषय सही हैं। परीक्षण करने के लिए **परीक्षण सूचना भेजें** बटन का उपयोग करें।
- **नेटवर्क कनेक्टिविटी जांचें**: पुष्टि करें कि **duplistatus** आपके NTFY सर्वर तक पहुंच सकता है। यदि लागू हो तो फ़ायरवॉल सेटिंग्स समीक्षा करें।
- **सूचना सेटिंग्स जांचें**: पुष्टि करें कि प्रासंगिक बैकअप के लिए सूचनाएं सक्षम हैं।

### उपलब्ध संस्करण दिखाई नहीं दे रहे हैं {/* #available-versions-not-appearing */}

यदि बैकअप संस्करण डैशबोर्ड या विवरण पृष्ठ पर नहीं दिखाए जा रहे हैं:

- **Duplicati कॉन्फ़िगरेशन की जांच करें**: सुनिश्चित करें कि Duplicati के उन्नत विकल्पों में `send-http-log-level=Information` और `send-http-max-log-lines=500` कॉन्फ़िगर किए गए हैं। Duplicati पहले N लॉग लाइनों को रखता है। यदि संस्करण सूची अभी भी गायब है, तो कैप बढ़ा दें या जब आप Duplicati निगरानी पर रिपोर्ट भेज रहे हों तो `0` का उपयोग करें। विस्तृत सूची गायब होने पर भी JSON आँकड़ों से संस्करण **गणना** दिख सकती है। देखें [लॉग लाइनें और उपलब्ध संस्करण](../installation/duplicati-server-configuration.md#log-lines-and-available-versions)।

### अतिदेय बैकअप अलर्ट काम नहीं कर रहे हैं {/* #overdue-backup-alerts-not-working */}

यदि अतिदेय बैकअप सूचनाएं भेजी नहीं जा रही हैं:

- **अतिदेय कॉन्फ़िगरेशन की जांच करें**: पुष्टि करें कि बैकअप के लिए बैकअप निगरानी सक्षम है। अपेक्षित अंतराल और सहिष्णुता सेटिंग्स की जांच करें।
- **अधिसूचना आवृत्ति की जांच करें**: यदि **एक बार** पर सेट किया गया है, तो अलर्ट केवल प्रति अतिदेय घटना में एक बार भेजे जाते हैं।
- **क्रॉन सेवा की जांच करें**: सुनिश्चित करें कि अतिदेय बैकअप के लिए निगरानी करने वाली क्रॉन सेवा सही ढंग से चल रही है। त्रुटियों के लिए एप्लिकेशन लॉग की जांच करें। पुष्टि करें कि क्रॉन सेवा कॉन्फ़िगर किए गए पोर्ट पर सुलभ है (डिफ़ॉल्ट: `8667`)।

### बैकअप लॉग एकत्र करना काम नहीं कर रहा है {/* #collect-backup-logs-not-working */}

यदि मैनुअल बैकअप लॉग संग्रह विफल हो जाता है:

- **Duplicati सर्वर एक्सेस की जांच करें**: सत्यापित करें कि Duplicati सर्वर होस्टनाम और पोर्ट सही हैं। पुष्टि करें कि Duplicati में रिमोट एक्सेस सक्षम है। सुनिश्चित करें कि प्रमाणीकरण पासवर्ड सही है।
- **नेटवर्क कनेक्टिविटी की जांच करें**: **duplistatus** से Duplicati सर्वर पर कनेक्टिविटी का परीक्षण करें। पुष्टि करें कि Duplicati सर्वर पोर्ट सुलभ है (डिफ़ॉल्ट: `8200`)।
  उदाहरण के लिए, यदि आप डॉकर का उपयोग कर रहे हैं, तो आप कंटेनर की कमांड लाइन तक पहुंचने के लिए `docker exec -it <container-name> /bin/sh` का उपयोग कर सकते हैं और `ping` और `curl` जैसे नेटवर्क टूल चला सकते हैं।

    ```bash
    docker exec -it duplistatus /bin/sh
    ping duplicati-server.local
    curl -I http://duplicati-server.local:8200
    ```

कंटेनर के अंदर DNS कॉन्फ़िगरेशन के लिए भी जांच करें (अधिक जानकारी के लिए देखें [Podman कंटेनर के लिए DNS कॉन्फ़िगरेशन](../installation/installation.md#configuring-dns-for-podman-containers))

- **Duplicati 2.4 और बाद के संस्करणों पर**, `/api/v1/systeminfo` एक खाली डिफ़ॉल्ट के साथ `machine-id` को सूचीबद्ध करता है। **duplistatus** Duplicati सर्वर सेटिंग्स से कॉन्फ़िगर किए गए आईडी को पढ़ता है। यदि संग्रह अभी भी सर्वर की पहचान नहीं कर सकता है, तो **Duplicati → सेटिंग्स → उन्नत विकल्प → मशीन-आईडी** सेट करें और पुनः प्रयास करें।

### पहले के संस्करण (0.9.x से पहले) से अपग्रेड करें और लॉगिन नहीं कर सकते {/* #upgrade-from-an-earlier-version-before-09x-and-cant-login */}

**duplistatus** संस्करण 0.9.x से उपयोगकर्ता प्रमाणीकरण की आवश्यकता है। एक डिफ़ॉल्ट `admin` खाता स्वचालित रूप से बनाया जाता है जब एप्लिकेशन को पहली बार स्थापित किया जाता है या पिछले संस्करण से अपग्रेड किया जाता है: 
    - उपयोगकर्ता नाम: `admin`
    - पासवर्ड: `Duplistatus09`

आप पहले लॉगिन के बाद [सेटिंग्स > उपयोगकर्ता](settings/user-management-settings.md) में अतिरिक्त उपयोगकर्ता खाते बना सकते हैं।

### एडमिन पासवर्ड खो गया या लॉक आउट {/* #lost-admin-password-or-locked-out */}

यदि आपने अपना व्यवस्थापक पासवर्ड खो दिया है या अपने खाते से लॉक आउट हो गए हैं (आप अभी भी `/login` खोल सकते हैं):

- **एडमिन रिकवरी स्क्रिप्ट का उपयोग करें**: डॉकर वातावरण में व्यवस्थापक एक्सेस की वसूली पर निर्देशों के लिए [एडमिन खाता वसूली](admin-recovery.md) गाइड देखें।
- **कंटेनर एक्सेस की पुष्टि करें**: सुनिश्चित करें कि आपके पास रिकवरी स्क्रिप्ट चलाने के लिए कंटेनर में डॉकर एक्सेस है।

यदि ब्राउज़र लॉगिन से पहले **एक्सेस अस्वीकृत** (HTTP 403) दिखाता है, तो यह एक [IP अनुमति सूची लॉकआउट](#locked-out-by-ip-allowlist) है, भूले हुए पासवर्ड नहीं। एडमिन-रिकवरी स्क्रिप्ट इसे बायपास नहीं कर सकती है।

### IP अनुमति सूची द्वारा लॉक आउट {/* #locked-out-by-ip-allowlist */}

यदि सेटिंग्स → [IP अनुमति सूची](settings/ip-allowlist-settings.md) एक गुम या गलत CIDR के साथ सक्षम है, तो प्रॉक्सी प्रमाणीकरण से पहले अनुरोध को अस्वीकार कर देता है। सामान्य लक्षण:

- पेज (`/`, `/login`, `/settings`, …) सादे-पाठ **एक्सेस अस्वीकृत** (HTTP 403) लौटाते हैं।
- सत्र और एडमिन एपीआई JSON `{ "errorCode": "IP_NOT_ALLOWED" }` लौटाते हैं।
- `/api/health` और `/api/ping` भी एक अनलिस्टेड आईपी से 403 लौटाते हैं जब भी कोई भी अनुमति सूची सक्षम हो। वे अभी भी लूपबैक से प्रतिक्रिया देते हैं। लॉगिन कुकीज़ मदद नहीं करतीं।

लॉकआउट के दौरान एप्लिकेशन चालू होने की पुष्टि करने के लिए, कंटेनर के अंदर से प्रोब चलाएं (लूपबैक को हमेशा अनुमति है):

```bash
docker exec duplistatus curl -sf http://127.0.0.1:9666/api/ping
```

सहेजने का पथ इसे रोकने का प्रयास करता है: आप तब तक **एडमिन** सूची को सक्षम नहीं कर सकते जब तक कि आपका मौजूदा IP पहले से CIDR में न हो (लूपबैक से सहेजते समय छूट देकर)। आप अभी भी खुद को बाहर का दरवाजा लगा सकते हैं जब आप एक CIDR का उपयोग करते हैं जो अब मिलता है लेकिन बाद में नहीं (VPN, DHCP, अन्य नेटवर्क), विश्वसनीय प्रॉक्सी को गलत विन्यस्त करके, या सूची को `127.0.0.1` / `::1` से उस पते को जोड़े बिना सक्षम करके।

पर्यावरण चर डेटाबेस को ओवरराइड करते हैं, इसलिए आप UI के बिना ठीक कर सकते हैं। वे सेटिंग्स को फिर से नहीं लिखते; प्रक्रिया उन्हें लेने के लिए पुनरारंभ की आवश्यकता है।

**एडमिन सूची को अक्षम करें** (सामान्य पुनर्प्राप्ति):

```bash
ADMIN_IP_ALLOWLIST_ENABLED=false
```

**या इसे सक्षम रखें और एक CIDR डालें जिसमें आपका मौजूदा IP शामिल हो:**

```bash
ADMIN_IP_ALLOWLIST=203.0.113.10/32
```

फिर एप्लिकेशन पुनरारंभ करें:

- **Docker Compose**: `docker-compose.yml` में `environment` के तहत समान कुंजियाँ सेट करें (फ़ाइल में टिप्पणी वाले उदाहरण शामिल हैं) और ऐप कंटेनर को फिर से बनाएं। `docker exec` चल रहे कंटेनर के पर्यावरण चर को नहीं बदलता।
- **स्थानीय / systemd**: सेवा वातावरण में चर को निर्यात करें और Next.js प्रक्रिया को पुनरारंभ करें (केवल cron सेवा नहीं)।

जब आप फिर से UI खोल सकते हैं:

1. लॉग इन करें और सेटिंग्स → IP अनुमति सूची में CIDRs और विश्वसनीय प्रॉक्सी ठीक करें।
2. वातावरण ओवरराइड को हटा दें ताकि सेटिंग्स फिर से सत्य का स्रोत बन जाए।

**बाहरी एपीआई** अनुमति सूची (`/api/upload`, `/api/summary`, `/api/lastbackup*`) डैशबोर्ड को लॉक नहीं करती है। इसे `EXTERNAL_API_IP_ALLOWLIST_ENABLED=false` या `EXTERNAL_API_IP_ALLOWLIST` के साथ उसी तरह से पुनर्प्राप्त करें। यदि Duplicati अपलोड HTTP 403 के साथ विफल होते हैं जब आप उस सूची को सक्षम करते हैं, तो [नए बैकअप नहीं दिख रहे](#new-backups-not-showing) देखें। विश्वसनीय-प्रॉक्सी पुनर्प्राप्ति `IP_TRUSTED_PROXIES` का उपयोग करती है (एक गैर-खाली मान भी ट्रस्ट-प्रॉक्सी का संकेत देता है)।

[IP अनुमति सूची](settings/ip-allowlist-settings.md#environment-overrides) और [पर्यावरण चर](../installation/environment-variables.md) देखें।

### डेटाबेस बैकअप और माइग्रेशन {/* #database-backup-and-migration */}

पिछले संस्करणों से माइग्रेट करते समय या डेटाबेस बैकअप बनाते समय:

**यदि आप संस्करण 1.2.1 या उसके बाद का उपयोग कर रहे हैं:**
- [सेटिंग्स → डेटाबेस रखरखाव](user-guide/settings/database-maintenance.md) में अंतर्निहित डेटाबेस बैकअप फ़ंक्शन का उपयोग करें
- अपना पसंदीदा प्रारूप (.db या .sql) चुनें और **बैकअप डाउनलोड करें** पर क्लिक करें
- बैकअप फ़ाइल आपके कंप्यूटर पर डाउनलोड हो जाएगी
- विस्तृत निर्देशों के लिए [डेटाबेस रखरखाव](settings/database-maintenance.md#database-backup) देखें

**यदि आप 1.2.1 से पहले के संस्करण का उपयोग कर रहे हैं:**
- आपको मैन्यली बैकअप लेने की आवश्यकता होगी। अधिक जानकारी के लिए [माइग्रेशन गाइड](../migration/version_upgrade.md#backing-up-your-database-before-migration) देखें।

यदि आप अभी भी समस्याएं अनुभव करते हैं, तो निम्नलिखित चरणों का प्रयास करें:

1.  **एप्लिकेशन लॉग का निरीक्षण करें**: यदि डॉकर का उपयोग कर रहे हैं, तो विस्तृत त्रुटि जानकारी की समीक्षा करने के लिए `docker logs <container-name>` चलाएँ।
2.  **कॉन्फ़िगरेशन को मान्य करें**: अपने कंटेनर प्रबंधन टूल (डॉकर, पोर्टेनर, पॉडमैन, आदि) में सभी कॉन्फ़िगरेशन सेटिंग्स को दोबारा जांचें जिसमें पोर्ट, नेटवर्क और अनुमतियाँ शामिल हैं।
3.  **नेटवर्क कनेक्टिविटी की पुष्टि करें**: सभी नेटवर्क कनेक्शन स्थिर हैं यह पुष्टि करें। 
4.  **क्रॉन सेवा की जांच करें**: सुनिश्चित करें कि क्रॉन सेवा मुख्य एप्लिकेशन के साथ-साथ चल रही है। दोनों सेवाओं के लॉग की जांच करें।
5.  **प्रलेखन देखें**: अधिक जानकारी के लिए इंस्टॉलेशन गाइड और रीडमी देखें।
6.  **समस्याएँ रिपोर्ट करें**: यदि समस्या बनी रहती है, तो कृपया [duplistatus गिटहब रिपॉजिटरी](https://github.com/wsj-br/duplistatus/issues) पर एक विस्तृत मुद्दा सबमिट करें।
